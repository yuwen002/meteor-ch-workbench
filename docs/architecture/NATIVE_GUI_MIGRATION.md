# 原生 GUI 迁移架构说明

## 目标与约束

本次迁移将桌面界面从 Wails WebView 逐步替换为 Gio 原生 GUI，保留 Go 业务逻辑、ClickHouse 驱动和现有本地数据格式。迁移期间旧 Wails + Vue 版本继续作为兼容基线，不提前删除。

- Community 核心采用 MIT 许可证。
- Pro 功能未来通过独立私有仓库和独立构建入口组合，不进入 Community 默认依赖。
- 不使用 Go `plugin` 作为跨平台扩展机制。
- 不以未经实测的框架宣传数据作为启动速度、内存或安装包体积结论。

## 目标分层

```text
GUI（Gio / 现有 Wails Adapter）
          |
          v
internal/app          应用服务编排，不依赖 GUI
          |
          +---- internal/config
          |
          +---- internal/clickhouse
          |
          +---- internal/platform（后续：文件、剪贴板、系统操作）
          |
          +---- internal/edition（后续：Community / Pro 能力接口）
```

## 当前落地

### 第一批：应用服务层起步

新增 `internal/app.Service`，由入口注入配置管理、查询历史、ClickHouse 服务和用户设置依赖。已将以下业务流程从根目录 Wails App 方法委托到该服务：

- 连接保存、删除、测试和断开。
- SQL 查询、查询取消和查询历史记录。
- DDL/DML 单条执行与批量执行。
- 数据库、表、视图、表结构和集群元数据读取。

根目录 `App` 暂时保留原有公开方法签名，作为旧前端兼容适配层；这样不需要一次性改写 Vue API，也不改变现有配置文件结构。

### 尚未迁移

以下能力仍由旧 Wails App 直接处理，后续分批迁移：

- 配置、历史、收藏 SQL、标签页和设置的完整应用用例。
- 文件打开 / 保存对话框与配置目录打开。
- 结果集导出到用户选择的文件路径。
- 剪贴板与系统通知等平台能力。

文件对话框等平台相关操作应移入平台接口及 Wails/Gio 各自的适配器，不能放入 `internal/app`。

## 迁移顺序

1. 为应用服务层补充可替换依赖与单元测试，并完成 Go 全量验收。
2. 把文件系统、对话框、剪贴板、打开目录等能力抽成平台端口。
3. 让旧 Wails 入口仅承担适配职责，确保旧版继续可构建。
4. 建立 Gio 主窗口与基础布局原型。
5. 验证 SQL 编辑器、结果虚拟表格、快捷键和主题能力，再决定是否投入完整 GUI 开发。
6. 最后建立 Community / Pro 构建组合和跨平台性能基准。

## 验收原则

每次迁移保持小步提交。每批至少执行 `gofmt`、`go test ./...`、`go vet ./...` 和 `go build ./...`；若当前执行环境无法运行测试，必须明确标注未验收，不能将代码推送或 CI 状态描述为通过。

原生 GUI 原型应以同一台机器、同一构建模式实测冷启动、空闲内存、查询期间内存、安装包压缩体积和大结果集滚动表现。目标值是优化方向，不是框架保证。
